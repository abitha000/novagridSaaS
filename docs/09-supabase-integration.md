## 2. What was implemented
- `src/lib/supabase.ts`: client using `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`, falling back to `utils/supabase/info.tsx`. PKCE flow (email links return `?code=`, compatible with hash routing). Throws if a `service_role` JWT is ever supplied.
- `src/lib/auth.tsx`: `AuthProvider` with session, sign-in, sign-up, sign-out, memberships (`tenant_users` → `organisations`), platform role, active organisation. **Schema probe:** calls `novagrid_schema_version()` (read-only). `live` only when version ≥ 8, else `demo` (prototype on sample data, with a visible badge).
- Registration: owner password added; `signUp` stores the form in `user_metadata.pending_registration` with an idempotency token. After the user confirms email, the app calls RPC `register_organisation` (creates organisation, owner membership, settings, pending approval, atomically). Unapproved organisations see only an "Awaiting approval" screen.
- Login: `signInWithPassword`, redirect to platform console or the organisation's industry workspace by **server-side** role.
- Route gate (`App.tsx`): platform routes need a `platform_users` row, workspace routes need an approved membership and the matching industry. The database remains the real authority (RLS).
- Data layer `src/lib/api/*`: organisations and admin RPCs, staff, contacts (soft delete, consent via RPC), notification templates/campaigns/recipients. Typed errors detect "schema missing".
- Live screens (`src/pages/LiveData.tsx`): Staff and People use real CRUD when live and an organisation is active.
- Notifications are **persistence only**: `create_notification` stores the campaign and recipient rows (`queued`/`skipped`). Nothing is sent, and the browser cannot write delivery statuses.

Not wired to live data yet: platform dashboards (organisations, approvals tables), payments, reports, industry modules, and the Compose screen's publish step. The API functions for the first of these exist.

## 5. Operations that must be done directly in Supabase (dashboard or CLI)
1. **Back up first** (or use a branch/staging project). Review `supabase/proposed-migrations/*.sql`, then apply 0001 to 0008 in order.
2. **Authentication → Providers → Email:** enable email confirmation (registration relies on it). Set a minimum password length (8+) and leaked-password protection.
3. **Authentication → URL configuration:** set Site URL to your deployed app URL and add the preview and local URLs as allowed redirects.
4. **Authentication → Rate limits / CAPTCHA:** enable CAPTCHA (Turnstile or hCaptcha) for sign-up and sign-in. Consider enabling MFA (TOTP) and requiring it for platform admins.
5. **Phone verification:** needs an SMS provider configured under Authentication → Phone. Until then `phone_verified_at` stays null (PRD gap).
6. **Create the first platform administrator:** sign up normally, then run in the SQL editor, replacing the email: `insert into public.platform_users (user_id, role) select id, 'super_admin' from auth.users where email = 'you@example.com';`. There is deliberately no self-service route to this.
7. **API settings:** confirm only `public` is an exposed schema (the `private` schema must not be exposed). Confirm RLS is enabled on `kv_store_5a875bd1` if the table exists.
8. **Edge Functions:** after approval, `supabase functions deploy invite-staff` (move it from `proposed-functions/`). Restrict CORS to your domain. Do not deploy before then.
9. **Database → Backups:** enable PITR on production and run a restore drill.
10. **Secrets** for Phase 7 providers via `supabase secrets set` or Vault.
11. Assumptions to verify: the `postgres` role has BYPASSRLS (Supabase default), Postgres 13+.
